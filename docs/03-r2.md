# Lab 3 — private access and verified multipart integrity

Read [R2 theory](00-theory.md#r2-a-key-addresses-an-object-not-a-video-pipeline) and complete [setup](setup.md). Use a dedicated private Standard bucket and bucket-scoped S3 Object Read & Write credentials.

## 1. Check the actual bucket and credentials

In dashboard, confirm public `r2.dev` and public custom-domain access are disabled. Then:

```sh
npm run r2 -- preflight
```

Makes a real prefix-limited S3 list request. This proves that request was authorized; it does not inspect every alternate public delivery route. The region is `auto`; the endpoint matches `R2_JURISDICTION`.

## 2. Upload the handout and inspect its key

```sh
npm run r2 -- upload
```

Uploads `samples/sample-document.txt` to `<random-run-prefix>/sample-document.txt`, recording the intended key before the request. The prefix is part of the exact object key, not a filesystem folder or an authorization boundary. Existing objects are refused rather than overwritten.

## 3. Use a temporary GET

```sh
npm run r2 -- presign --expires 60
```

Prints a complete, locally signed SigV4 GET URL. Navigate to it immediately in a new browser tab. Expect the sample document to load. Preserve method, host, path and query; the S3 hostname cannot be changed to a custom domain.

Signing alone contacts no R2 service and proves neither existence nor permissions. A browser JavaScript `fetch` would additionally need CORS; this lab uses navigation and terminal GET, without editing bucket CORS.

## 4. Check a fresh expiry request

```sh
npm run r2 -- verify-access --expires 5
```

Requests the unsigned S3 path, then the valid signed GET, then the **same** signature after expiry. Expected: unsigned denied → signed succeeds → expired denied. GET is deliberate; HEAD would be a different signed operation. Separately confirming no public alternate bucket routes is still required.

## 5. Generate and upload in real parts

```sh
npm run fixture
npm run r2 -- multipart
```

The local binary is exactly 12,582,912 bytes with a deterministic SHA-256. The live upload creates an upload ID, persists it locally, sends **5 MiB + 5 MiB + 2 MiB**, collects ETags, and completes in part-number order. The AWS SDK bounds each request to three attempts, retaining completed parts while retrying a failing request. On terminal operation failure, the command attempts to abort the exact owned incomplete upload.

This is a teaching example; 12 MiB does not require multipart in production. It has no cross-process part-resume feature. After a hard interruption, inspect the recorded upload ID and dashboard before cleanup/retry.

## 6. Download the object and verify every byte

```sh
npm run r2 -- verify
```

Reads the actual completed object through authenticated S3, checks the byte count, computes SHA-256 and compares it to the source recorded before upload. Saves the validated bytes in `lab-output/multipart-downloaded.bin`. Matching old local output is retained; a differing file is never overwritten. ETags are used for multipart completion, not substituted for the content checksum.

Inspect the object in dashboard as well. Strong storage consistency applies after completion; a separately cached custom-domain path may still have stale responses.

## 7. Explain and clean up

Record bucket, jurisdiction, owned keys, part sizes, access statuses and matching hashes. Then:

```sh
npm run r2 -- cleanup
```

Aborts a recorded incomplete upload and deletes only this run's recorded object keys. It leaves the bucket, credentials, CORS and other prefixes untouched. Delete the dedicated empty bucket and revoke workshop credentials in the dashboard when you no longer need them. Generated local files are Git-ignored.

## Recovery

- `AccessDenied`: check bucket scope, Object Read & Write and propagation. A REST bearer token is not an S3 key pair.
- `SignatureDoesNotMatch`: verify exact host/method/key, query and system clock.
- Browser fetch error but terminal GET works: inspect CORS independently from authorization.
- Upload failed: inspect `.lab/state.json`; cleanup the owned intent/upload before restarting. Never assume an unknown network outcome created no resource.
- Lost ledger: recover owned IDs/keys/upload IDs from dashboard and recorded non-secret observations; do not run bucket-wide deletion.
